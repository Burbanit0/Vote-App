# EXP-021 — Suite e2e Playwright sur un build de production plutôt que le serveur de dev

- **Date** : 2026-09-25 (correctif) → 2026-09-26 (merge PR #649) · **Statut** : adopté · **Coût réel** : non chronométré précisément dans la PR (voir « Ce que ça a coûté » pour ce qui est mesurable indirectement) · **Coût en tokens** : partagé avec EXP-019/EXP-020 et une partie d'EXP-022 — voir la note de coût d'EXP-019 (session continue `c08db11e`, non ventilable par sujet)
- **Verdict en une phrase** : servir la suite e2e depuis un build de production (`vite build && vite preview`) au lieu du serveur de dev Vite réduit le nombre de requêtes de module par navigation de 59-127 à 17-39, éliminant un flake WebKit qui a laissé une page blanche 5 fois sur ~400 runs en dix jours — 0 flake de cette forme mesuré depuis, et deux races de navigation trouvées et corrigées au passage.

## Hypothèse de départ

Entre le 2026-09-15 et le 2026-09-25, la suite e2e Playwright (gate obligatoire sur toute PR, `.github/workflows/e2e.yml`) a montré 5 flakes exclusivement WebKit sur environ 400 runs, toujours de la même forme : une requête de module perdue en cours de navigation, laissant soit une page blanche (`navigation.spec.ts:35`, 4 fois), soit un échec de chargement d'un module paresseux (« Importing a module script failed »), soit une erreur interne WebKit sur `goto` (`i18n.spec.ts:69`, 1 fois). La navbar se rend hors de tout `Suspense`, donc une page blanche signale une requête perdue, pas un rendu lent — ce diagnostic (fait par une session `flake-hunter`, l'agent décrit au Lot 11 du plan de solidité) a orienté l'hypothèse testée : **si le serveur de dev Vite émet des dizaines de requêtes de module non regroupées par navigation, et que WebKit en perd une de façon intermittente, servir un build de production — celui qui expédie réellement — devrait réduire ce nombre de requêtes et donc la fenêtre d'exposition au flake.** C'est un pari testable, pas acquis d'avance : rien ne garantissait que WebKit perdrait moins de requêtes simplement parce qu'il y en a moins, ni que basculer sur un build ne romprait pas autre chose (web sockets, variables d'environnement, service workers).

## Protocole

Modification de `voter-app/playwright.config.ts` (commit `f7c5f6f8`, PR #649) :

1. **`webServer.command`** passe de `npm start` (serveur de dev) à `npx vite build --outDir node_modules/.e2e-build && npx vite preview --outDir node_modules/.e2e-build --port 3000 --strictPort` — un `outDir` dédié pour ne jamais écraser ni entrer en course avec `build/` de `npm run build` (une build de couverture laissée dans `build/` avait fait échouer `size-limit` à 1,24 Mo lors de la revue). `timeout` passe de 60 s à 180 s pour inclure le temps de build.
2. **`serviceWorkers: 'block'`** — un build de production enregistre le service worker de `vite-plugin-pwa` ; un test doit voir le réseau, pas le précache d'un worker.
3. **Variables d'environnement Umami vidées** (`VITE_UMAMI_SRC`, `VITE_UMAMI_WEBSITE_ID`) — un build lit `.env.local`/`.env.production`, qu'un serveur de dev servi par `npm start` ne lisait pas de la même façon ; sans ce vidage, la configuration de suivi d'un mainteneur aurait compté les vues de page de test.
4. **`ws: true`** ajouté à la règle de proxy `^/api/` (`voter-app/vite.config.ts`) : sous le build, le flux Socket.IO du Monte-Carlo se connecte en same-origin à `/api/v2/socket.io`, que le proxy ne mettait pas à niveau (upgrade WebSocket) — le test e2e du Monte-Carlo a échoué au premier run local sans ce drapeau. L'entrée de proxy racine `/socket.io`, inutilisée depuis que le flux est passé sous `/api/v2`, est supprimée avec les mentions qui la nommaient.
5. **Deux races de navigation corrigées dans les specs eux-mêmes**, trouvées par la revue (`/code-review max`, deux passes) : la boucle de vérification de navbar n'attendait que la navbar (hors Suspense), laissant les chunks paresseux de la surface précédente en vol à chaque `goto` — déplacée dans le test par-surface, après l'ancrage de cette surface (mesuré 10/10 runs par la revue) ; `switchToEnglish` n'attendait rien, donc le `goto` suivant interrompait le changement de langue — les dix tests « aucune clé non traduite en anglais » rendaient en fait du français (0/40 en anglais dans les runs de la revue), qu'une fuite anglaise plantée avait laissée passer sans échec ; corrigé en attendant la navbar anglaise.
6. **Couverture CORS préservée séparément** : les appels same-origin sous le build n'envoient plus de préflight CORS, donc `test_cors.py` (backend) épingle désormais explicitement le préflight `localhost:3000` que la suite e2e ne couvre plus.

Rejouable en relançant `npm run test:e2e` (`voter-app/`) après ces changements, avec le backend sur `:4434`.

## Ce que ça a trouvé

**Le nombre de requêtes par navigation, mesuré et écrit dans le commentaire de configuration lui-même** (`playwright.config.ts`) : le serveur de dev en émet 59 à 127 par navigation, contre 17 à 39 pour le build — un facteur de 3 à 4, qui réduit directement la fenêtre où WebKit peut perdre une requête sans que le mécanisme sous-jacent (pourquoi WebKit en perd une) ait besoin d'être élucidé plus finement.

**Les deux races de navigation, chacune mesurée en direct par la revue, pas supposées** : la boucle de vérification navbar défaillante à 10/10 runs, et les dix tests « anglais » qui rendaient 0/40 fois réellement en anglais avant le correctif, avec une fuite anglaise plantée passant tous les tests malgré cela — la preuve qu'ils ne testaient pas ce qu'ils prétendaient tester.

**Une dépendance cachée révélée par le changement d'environnement, pas par les specs eux-mêmes** : le test e2e du Monte-Carlo a échoué dès le premier run local sous le build, à cause du proxy WebSocket manquant — un défaut qui existait probablement déjà en configuration de production (le proxy `^/api/` de dev n'upgradait pas non plus), révélé seulement parce que le build, contrairement au serveur de dev, force une connexion Socket.IO réellement proxée.

**Zéro flake de cette forme mesuré après le changement** : le résultat n'est pas seulement théorique (moins de requêtes). Une investigation `flake-hunter` ultérieure sur un flake « res-table » de la PR #645 a établi que ce run précis avait démarré *avant* le merge de #649 (encore sur le serveur de dev) — cohérent avec l'historique de merge-queue observable sur #645 elle-même : sa tentative de fusion du 2026-09-26 22:49-23:47 UTC (avant le merge de #649 à 23:58:32) a échoué sur plusieurs checks dont Playwright E2E, tandis que sa tentative suivante, en file de 03:08 à 03:18 le 2026-09-27 (après #649), a réussi sans accroc. Le rapport `flake-hunter` de la séance (2026-09-27, non versionné) le confirme directement : run 36279747572, `laboratoire.spec.ts:68`, famille « theory », puce `chip-res-table` restée sur « Chargement… » 20 s sous WebKit puis passée au retry. Le commit testé (`pull/645/merge` = `24fca26`, base `d13f44b`) avait encore `webServer: npm start` (serveur de dev) ; la trace du retry montre des modules non bundlés (`/@vite/client`, `/src/components/playground/FullResultsModule.tsx`…), soit 8 requêtes de module pour cette seule puce. C'est le même mécanisme de module perdu, tombé sur une autre fiche. Les 10 runs e2e environ lancés après le merge de #649 (develop et PR) étaient verts.

## Ce que ça a coûté

Non chronométré précisément dans la PR : ni le temps de build ajouté par run CI (le `timeout` passe de 60 s à 180 s pour l'inclure, un plafond, pas une mesure), ni le temps de la double passe locale. Ce qui est mesurable indirectement dans le corps de la PR : suite locale passée deux fois sur trois moteurs (chromium, firefox, mobile), 239/239 les deux fois (2 tests de moins que `develop`, parce que la boucle navbar a été déplacée dans les tests par-surface plutôt que supprimée) ; deux passes de `/code-review max` (la première a trouvé les deux races de navigation et les problèmes de partage de `build/`/fuite d'environnement, tous corrigés dans la même PR) ; `tsc --noEmit`, `eslint` (0 erreur), `prettier`, `sonarjs` maintenu à 265. WebKit lui-même n'a pas pu être vérifié en local (le bac à sable de développement ne peut pas faire de requêtes HTTP sous WebKit) — seul CI pouvait confirmer le comportement sur le moteur concerné par le flake d'origine.

Reconnu explicitement non traité dans la PR (marqué « follow-up », pas un coût caché découvert après coup) : `reuseExistingServer` réutilise silencieusement un serveur de dev déjà lancé sur :3000 en local ; le mode UI/watch de Playwright ne reconstruit qu'une fois par session ; un build de production masque les détails de développement de l'ErrorBoundary dans les captures d'échec ; `trace: 'on-first-retry'` ne trace jamais la première tentative d'un flake (seule la revue elle-même a mesuré les deux races directement, sans dépendre de cette trace).

## Verdict et pourquoi

**Adopté.** Le changement traite la cause structurelle mesurée (nombre de requêtes par navigation) plutôt que le symptôme (retenter le test) : c'est un build de production qui expédie réellement, pas un artefact de test seul, donc l'e2e teste enfin ce qui part en production. Les deux races de navigation trouvées par la revue étaient des défauts réels indépendants du changement de serveur — corrigés dans la même PR parce que découverts pendant la même revue obligatoire, pas ajoutés après coup. La confirmation empirique (zéro flake de cette forme depuis, dans la mesure où l'historique de merge-queue de #645 le suggère) reste une observation de fenêtre courte, pas une preuve statistique équivalente aux 400 runs qui avaient révélé le problème initial.

## Ce que j'en retiens (transférable à un autre projet)

1. **Un flake « aléatoire » et rare (5 sur 400 runs) sur un seul moteur de test mérite d'être caractérisé par sa forme exacte avant d'être corrigé** — ici, trois symptômes de surface (page blanche, échec d'import de module, erreur interne au `goto`) partageaient la même cause structurelle (une requête réseau perdue), visible seulement en comptant *combien* de requêtes chaque navigation émettait dans chaque configuration candidate.
2. **Tester sous l'artefact qui expédie réellement, pas sous un serveur de développement pratique pour itérer, élimine une classe entière de divergences environnementales** (nombre de requêtes, enregistrement de service worker, lecture de fichiers `.env`) d'un coup, plutôt que de les corriger une par une au fil des flakes qu'elles causent.
3. **Un changement d'infrastructure de test (ici : la manière de servir l'app) est aussi l'occasion de vérifier, pas de supposer, que les specs existants attendent réellement la bonne chose avant d'agir** — une revue systématique (`/code-review max`) sur ce changement a trouvé deux races de navigation préexistantes que le changement de serveur n'avait pas causées mais rendait plus visibles à investiguer.
4. **Un changement d'environnement de test peut révéler une dépendance de production jusque-là masquée** (ici, un proxy WebSocket manquant) parce qu'il force un chemin réseau que l'ancien environnement de test ne sollicitait pas de la même façon — traiter cette découverte comme un signal sur la configuration de production elle-même, pas seulement comme un obstacle à lever pour faire passer les tests.
